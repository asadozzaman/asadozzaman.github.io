The model is one part of the pipeline.

A video run needs more than boxes on a screen. It needs a clear record of what happened: which configuration ran, how tracks were assigned, where time went, and which output files are complete.

This project separates detection, tracking, and output handling behind typed interfaces. The result is a working baseline that can be inspected and extended without putting every concern in the model loop.

One run. Several useful outputs.

Read video and configurationLocal video and model weights; explicit effective settings.
Detect and associateYOLO detections pass through typed objects to a ByteTrack adapter.
Write inspectable artifactsAnnotated MP4, frame JSON, track CSV, and a run summary.

Decisions that matter

  • Separate interfaces. Detection and track types keep library-specific outputs out of the rest of the application.
  • Bounded output memory. Frame and CSV records stream to disk rather than accumulating decoded images.
  • Explicit completion. The output-directory workflow writes to a temporary location before publishing a completed run.
  • Traceable timings. Inference throughput and end-to-end throughput are reported separately.

What this establishes: a recorded functional run with inspectable output. It is not an accuracy score, a controlled hardware comparison, or a ground-truth count. The 42 track IDs must not be read as 42 correctly counted objects. The CPU model and a redistributable input-video reference are not recorded.

Automated CPU checks cover selected adapter and serialization behavior. They do not rerun the video experiment or measure detection and tracking accuracy.
